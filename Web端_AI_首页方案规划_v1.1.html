01背景与定位

当前 Web 仍是「浏览器版客户端」：菜单 / Tab 是入口，AI 能力覆盖在各页面的小气泡入口和侧边栏唤起的阶段。Web 用户在研究 / 决策密度可以远高于 App，但现在 AI 能力应用较弱。本轮规划把 Web 首页升级为 AI 主导的工作台。

一句话定位

在不离开页面的前提下，让用户通过「目的表达 → 意图识别 → 伪生成式界面」完成扫场 → 研究 → 决策 → 监控 → 复盘的全闭环。监控由 AI 工作台 #aw 持续承担，不构成独立路径；应急情境从「为什么跌了」类输入触发，归并到归因路径。

3 阶段产品形态演进

阶段形态说明
当前 / 本期 目的表达 → 意图识别 → 伪生成式界面 主区由 6 类预设动态视图按意图组合，不是模型实时画 UI。本规划落到这一格。
中期 目的表达 → 意图识别 → 生成式界面 主区由模型在预设骨架上动态填充，预设视图退化为兜底；生成式组件按上下文实时组合。
终局 目的表达 → 托管 → 结果与中间控制权 用户给目标，Agent 自主执行；中间环节按需暴露控制权，结果按需呈现。

3 个产品形态设计

形态含义落地体现
意图表达是唯一入口 入口不是输入框、按钮或菜单，而是「意图表达」——文本、语音、点选、上下文都是载体。输入框只是当前阶段的物理承载。 底部输入框承载文本与语音；live morph 在打字阶段就重组主区；菜单 / Tab 不再是主路径。
伪生成式交互区 主区是「按意图组合的预设动态视图」——这是当前阶段对生成式界面的最近近似，并非模型实时画 UI。 6 类 dyn-* 视图 + classifyIntent 命中规则；输入 NVDA → 主区 13 行结构化 + chat 7 段富分析。
Agent 调度机制 不同意图调度不同 Agent，每个 Agent 有自己的任务边界与执行步骤——不是助理人格，是任务执行单元。本期是单 Agent 派遣，跨 Agent 接力 / 委托放在后续阶段。 4 类 Agent（选股 / 深度 / 大盘 / 持仓风险）独立调度；色 / 动效 / 步骤指示器各自不同，标识当前在执行哪类任务。
规划原则

不被 App 形态约束。大屏、长会话、多面板是 Web 的优势，所有结构选择优先服务「在一屏完成多动作」。

03意图表达即入口 · live morph 与意图识别

「意图表达是唯一入口」落地的关键，是把主区视图切换 / Agent 面板打开从「Enter 触发」前移到「打字阶段触发」。每多输入一个字符，主区都可能在重组——这是与「先 Enter 后渲染」最大的体验差异。

04Agent 调度机制 · 4 类任务执行单元

Agent 不是助理人格，是任务执行单元。不同意图调度不同 Agent，每个 Agent 在 #dp 面板独立展示其任务边界与执行步骤（理解 → 采集 → 整合）。色 / 动效 / 步骤指示器各自不同，目的是让用户判断当前在执行哪类任务。本期是单 Agent 调度——一次意图触发一类 Agent；跨 Agent 接力 / 委托放在后续阶段。

这一期做

  • 4 类 Agent 的任务边界与视觉差异化
  • 3 步骤指示器随 chat 节奏推进
  • Agent 面板 live 阶段同步打开
  • 主区切换不影响 Agent 面板状态

这一期不做

  • Agent 之间的接力 / 委托（多 Agent 协同）
  • 用户自定义 Agent 触发关键词
  • Agent 历史会话的独立存档（暂复用 chat 历史）
  • dyn-compare 的专属 Agent（待补，参见 §05）

视图与 Agent 的关系

主区视图 = 「看的东西」（界面），Agent = 「做的事」（任务）。同一视图（如 dyn-research）从不同入口被打开，只要意图属于「深度分析」，调度的都是同一个 Agent —— 任务身份稳定，不随入口变。dyn-compare 是股票 PK 的衍生场景，专属 Agent 待补；dyn-tradeplan 是结构化编辑，不需要独立 Agent。

08待对齐的问题

下列问题需要在工程拆解前与相关方对齐。每一项都会显著影响产品形态或工程投入。

  1. 意图识别的兜底策略。关键词命中是确定性方案，但用户提问形式千差万别（如「这只票还能拿吗」）。是否引入 LLM 意图分类？引入后对响应延迟与命中率的预期？建议先用关键词覆盖 80% 主路径，LLM 兜底剩余 20%，并设置降级链路。
  2. 动态视图的覆盖优先级。6 类视图工程量不一致。建议按"用户场景渗透率 × 实现复杂度"打分：dyn-research / dyn-risk / dyn-attribution 优先；dyn-screener / dyn-tradeplan 次之；dyn-compare 最后。需与数据团队对齐 nvdaDetail 等结构化数据的真实接入节奏。
  3. Agent 命名与边界。当前 4 类 Agent 用功能性命名（"持仓风险 Agent" 等），强调任务边界而非助理身份。其中"持仓风险 Agent"在 v1.0 文档中曾命名为"复盘分析 Agent"，本版改为贴合实际功能（demo 端代码同步将在下次迭代落地）。是否进一步语义化（如"风险代理人"等术语）会影响品牌调性，需与设计、品牌团队对齐。
  4. chat 富气泡的合规与法务。lbaiAttributionChat 的 11 个 .ch-cite 来源是合规设计的关键。需与法务确认：①来源标注的最低标准；②"形态识别 / 场景推演"与"投资建议"的边界文案；③免责说明在每段气泡的呈现位置。
  5. 工作台与现有持仓 / 订单系统的对齐。AI 工作台 5 状态（激活 / 运行 / 正常 / 预警 / 暂停）涉及订单生命周期。需与交易系统团队对齐：状态切换的事件源、Move forward 创建任务的实际执行链路、监控触发条件的可配置范围。
  6. chat 列宽度持久化的跨设备策略。当前 localStorage 只在本地保存。是否需要云端同步用户偏好（chat 宽度 / 默认展开状态 / Agent 偏好）？这会与 App 端长期账号体系打通需求挂钩。
  7. 分阶段上线节奏。建议拆分为：阶段一只做"意图入口 + 主区动态切换 + 通用 chat"（核心叙事跑通）；阶段二补"4 类 Agent 任务边界 + 富 chat 7 段"；阶段三补"AI 工作台 + Move forward 闭环"。三阶段是否各自独立可上线，需与工程负责人对齐。
